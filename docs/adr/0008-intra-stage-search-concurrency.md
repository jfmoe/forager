# Intra-stage search concurrency and blocking IO boundary

forager parallelizes independent provider work inside each pipeline stage while keeping the stage boundaries themselves sequential. The classifier, main search, and supplemental capabilities still run one after another, and capabilities still run only after main search succeeds; provider fallback chains inside a seam stay strictly ordered (primary-first, per the timeout budget ADR).

**Concurrency happens at three fan-out points.** The supplemental capabilities of a search run concurrently with each other (web_fetch fans out over the URLs found in the query); research flattens its subquestion × capability loop into one concurrent task list; research candidate fetching runs in bounded waves. Everything else stays sequential.

**The fan-out limit is a hard-coded constant, `FANOUT_CONCURRENCY = 4`, with per-fan-out semantics.** Each fan-out point independently bounds its own in-flight work; there is no shared global capacity, so nested fan-outs can momentarily exceed four requests in flight (three capabilities plus four fetch URLs peaks at seven). The limit is not a config key: raising it trades against provider rate limits, and neither direction has a user who can judge that trade better than the default.

**Concurrent branches do not split the deadline.** All branches share the one absolute `Deadline`; each sees the same remaining wall-clock time, so the serial-era motivation for `slice_budget` between siblings disappears. Inside each branch the auxiliary-seam rules of the timeout budget ADR are unchanged: per-attempt `timeout` caps plus provider-chain slicing.

**Candidate fetching runs in waves sized `min(4, evidence still needed)`.** Each wave is a `join_all` over the next distinct candidates (URL dedup happens when the batch is assembled, at a single point); successes count toward `max_evidence`, failures record gaps, and the loop refills until the quota is met or candidates run out. Success paths never overfetch and never race candidates against each other, so no provider quota is spent on results that get discarded.

**Merge order is deterministic; result content is not guaranteed to match the serial version.** Fan-outs use order-preserving primitives (`join_all`, `stream::buffered` — not `buffer_unordered` or `JoinSet`), and each branch's attempts, sources, gaps, and diagnostics are appended as a block in launch order, which equals today's serial order. But concurrency changes which requests get budget: branches that a serial run would have starved can now succeed, so journals and sources may contain more (occasionally different) entries under the same deadline. This is a behavioral change, not a pure performance change; the invariants are ordering and field structure, not byte equality.

**Credential claims serialize through a process-wide async mutex and run on the blocking pool.** `claim()` performs a file lock spin, fsync, and rename; calling it inline stalled runtime workers, and concurrent claims could time out against each other's file lock and collapse rotation onto index 0. Claims now queue on one `tokio::sync::Mutex` and execute inside `spawn_blocking`, with the owned guard moved into the blocking closure so cancellation of the waiting future cannot release the lock while a file transaction is still running. Cursor semantics, the state file format, and cross-process rotation are unchanged; the queue wait happens before attempt timing starts and is not part of attempt duration.

**The runtime stays `new_multi_thread`.** All fan-out concurrency is intra-task IO multiplexing, which a current-thread runtime could serve, but synchronous CPU segments (SSE event parsing, multi-MiB body decoding) run on the executor thread and the command flow spans several `block_on` calls; switching is deferred until tail-latency measurements under four-way fan-out justify it.

**Accepted consequences:** concurrent branches that share a provider amplify burst pressure on it, including simultaneous credential rotations after matching 429s — a per-provider gate is a future option, not part of this decision; a slow fetch in a wave blocks the next wave (head-of-line), and `quick` (one evidence item) degrades to serial fetching; worst-case total requests per fan-out branch remain credential count + `retry.max_attempts` − 1, multiplied by the fan-out width. Implementations must not drop in-flight futures mid-way (a cancelled request can have upstream side effects that never reach the journal) and must enable the tokio `sync` feature explicitly.
