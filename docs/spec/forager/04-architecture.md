# 4. Rust 架构骨架

权威来源：[#58 Resolution](https://github.com/jfmoe/smartsearch/issues/58) 及其[补充决议（F1–F10）](https://github.com/jfmoe/smartsearch/issues/58#issuecomment-5078828791)。选型输入：#54（clap 4 derive、tokio + reqwest(rustls)、figment + serde、thiserror/anyhow/miette、dist + release-plz；aichat 为架构参考）。

## 工程形态：单 crate `forager`，bin + lib

不上多 crate 工作区（Rust 模块私有性已在编译期阻止跨私有面 import；单 crate → 工作区是机械重构）。两条纪律：① 模块默认私有，`lib.rs` 对外只开放 `app`、`config`、`types` 三个必要门面；跨模块共享必须显式 `pub(crate)` 且只能上移共享层，provider adapter 之间禁止横向 import；② `main.rs`/`lib.rs` 分离，bin 只负责 clap 解析、输出渲染与退出码映射。

## 六分组物理结构与五层单向依赖

`src/` 以职责形成六个物理分组；`lib.rs` 用显式 `#[path]` 声明保持既有 crate 内模块名，不把目录本身变成新的公共 API 层级。

- **`cli/`**：CLI 参数定义、应用分发与 `app` 公共门面；参数树在 `args.rs`，分发在 `dispatch.rs`；`forager platform` 命令组的静态参数树与分发在 `platform.rs`，`forager gemini` 命令组的在 `gemini.rs`，`forager chatgpt` 命令组的在 `chatgpt.rs`；委托研究报告的落盘规则在 `delegated_report.rs`，由各 `research result` 命令共用；二进制侧的 Gemini 与 ChatGPT 结果渲染分别在 `gemini_render.rs` 与 `chatgpt_render.rs`，两者共用的渲染结果与带会话 URL 的失败渲染在 `delegated_render.rs`，平台命令（search 与 videos 等分页结果页、fetch 结果、按平台的 comments 与 ask、YouTube transcribe 与 HN stories）的渲染在 `platform_render.rs`，四者都由 `main.rs` 声明为 bin 私有模块，不属于 lib。
- **`core/`**：engine（各 seam 的 provider 链）、platform_chain（平台 route 规划、cursor 与分页操作链：search、Google Scholar cited-by 与 YouTube videos）、platform_fetch（平台 fetch 的元数据链与正文段）、platform_comments（comments 这一单 route L2 操作的规划与 route 链，按平台分派小红书与 YouTube）、platform_ask（ask 这一单 route L2 操作的规划与 route 链，按平台分派 X 与 YouTube）、platform_precheck（YouTube 模型操作请求模型之前经 YouTube fetch 链读取视频的前置检查，以及它的 attempts 与诊断排在模型 route 链之前的合并）、platform_transcribe（YouTube transcribe 这一单 route L2 操作的规划与 route 链）、platform_stories（Hacker News stories 这一单 route L2 操作的规划与 route 链）、platform_checklist（仅测试构建：新平台接入清单一致性检查）、search_fanout（普通 search 的辅助能力 fan-out 与结果合并）、chain、classifier 与 Attempt Trace。
- **`capabilities/`**：Capability Catalog 与 platform catalog、Provider Credential Pool、跨进程限速（`rate_limit`）、Provider HTTP Read Contract（`net`）及 provider adapter（含平台 route adapter）；capability provider 与委托研究供应方的构造函数，以及按注册信息组装访问限速器与 Provider Credential Pool 的助手，在 `providers/constructors.rs`，经 `providers` 再导出。
- **`evidence/`**：Research Evidence Pipeline、Search Result Journal 与 stderr attempt log。
- **`infra/`**：config、secure filesystem、共享私有状态文件（`state_file`）、redaction 与零 IO 的 `types` 基底。config 的加载在 `config/load.rs`：读取配置文件、按 schema 反序列化并交给校验；规则校验在 `config/validate.rs`：加载时校验整份配置，`config set` 写入前按同一 schema 规则校验单个值；`config/view.rs` 生成凭据安全的有效配置视图。
- **`ops/`**：doctor 与 smoke 运维入口。

物理分组表达职责归属，调用关系仍遵守五层从上到下的单向纪律：

```
入口（main）
  → 应用（cli/app、args、dispatch）
    → 能力编排（engine、platform_chain、platform_fetch、platform_comments、platform_ask、platform_precheck、platform_transcribe、platform_stories、search_fanout、research、classifier、doctor、smoke、journal）
      → 能力基础设施（catalog、providers、credentials、rate_limit、net、config、secure_fs、state_file、redact）
        → 类型基底（types）
```

上层可以依赖下层，下层不得反向依赖上层；同层共享行为必须放到该职责的唯一拥有模块，再以最窄的 crate 内可见性提供。`catalog` 独立于 config 与 providers，二者只单向消费它；`catalog` 只从 `rate_limit` 取访问策略类型，`rate_limit` 不依赖 `catalog`。provider adapter 只消费 `providers/shared`、`providers/execution`、`providers/opencli`、`providers/opencli_route`、`providers/markup`、`providers/transcript`、`providers/youtube_transcript` 等共享拥有模块，不互相 import；`providers/markup` 把平台接口返回的 HTML 或 JATS 标记转成纯文本（去标签、还原实体、折叠空白），由 `ssrn_crossref` 与 `ssrn_browser` 共用，它的实体还原另由 `youtube_api` 用于 search 的标题与描述片段，`youtube_web` 用它把字幕分段的 HTML 转成纯文本；`providers/transcript` 拥有 Transcript（一个视频按时间分段的文字）的模型与渲染（见「YouTube 职责」），与平台无关，只依赖 `types`，不依赖任何 route adapter；`providers/opencli` 是 OpenCLI 进程传输（启动命令、进程组与截止时间、有界读取、OpenCLI 2.x 输出外壳与退出码映射；窗口模式由每条命令在 `OpenCliCommand` 中声明，传输只把它写进调用参数），不含任何站点知识，也不反向依赖 route adapter；`providers/opencli_route` 是绑定具体 route 的 OpenCLI 调用，持有 route 身份及其注册的 adapter、执行配置（`command`、`timeout`）、限速器与请求截止时间，为 adapter 命令构造调用（命令名、选项、窗口），生成该 route 的执行设置（provider 名、调用方给定的操作目标与重试策略、attempt 超时、`process` 传输标签），并执行命令：`run` 返回带 status 的外壳，供需要区分 `no_results` 的调用方（SSRN）使用，`read` 只返回页面事实，遇到 `no_results` 统一报 Runtime；四个 OpenCLI route 都经它调用传输，页面事实的判定与措辞仍归各 route 所有；平台 route adapter 同样不 import 任何 capability provider。平台 fetch 的正文段由编排层的 `platform_fetch` 调用 `engine::fetch`，route adapter 只声明候选正文来源（一组 URL，或一个已校验的本地文件）。

- **应用组合层**（F1）：`cli/app.rs` 只公开参数与分发门面；`dispatch.rs` 先构造共享 `NetworkDependencies`，再按命令建立 `AppContext<P>`、`FetchContext`、`SearchContext` 或 `ResearchContext`，各自持有所需的 runtime、配置与网络依赖。provider 实现与路由策略留在下层模块，Search Result Journal 仍由分发层在命令终态统一落笔。
- **`types` 类型基底**：零 IO 纯类型层——ErrorKind、ProviderError、Capability、`PlanCapability`（plan 语境独立两值枚举）、各 Outcome、ProviderAttempt、Source、ResearchPlan Schema v1、Deadline、薄正文阈值常量，以及平台形状（Platform、Platform Ref 与 canonical URL 推导、Content Depth、平台选项、条目、结果页与 fetch 结果）。所有跨层形状的唯一定义点。`infra/types/` 是目录模块，按职责分为 `capability`、`research`、`error`、`attempt`、`search`、`outcome`、`platform`、`platform_arxiv`、`platform_ssrn`、`platform_ssrn_search`、`platform_scholar`、`platform_xiaohongshu`、`platform_xiaohongshu_comments`、`platform_x`、`platform_hn`、`platform_youtube`、`platform_youtube_comments`、`platform_youtube_videos`、`platform_youtube_model`、`delegated_report`、`gemini_research`、`chatgpt_research`、`deadline` 私有子模块，由 `mod.rs` 统一再导出，公共路径保持 `forager::types::*`。`platform` 叶子只放各平台共享的形状（Platform、Platform Ref、Content Depth、平台选项、条目、结果页与 fetch 结果的外层枚举与结构）；每个平台自己的形状放在该平台的类型叶子中：arXiv 的 ref、选项、条目字段与校验由 `platform_arxiv` 拥有；SSRN 的 ref 与条目字段由 `platform_ssrn` 拥有，搜索选项与校验由 `platform_ssrn_search` 拥有；Google Scholar 的 ref、搜索选项与校验、条目字段（search 结果与 fetch 的版本列表）由 `platform_scholar` 拥有；X 的 ref、snowflake 发布时间推算、search 与 ask 共用的选项与校验、帖子与 thread 字段，以及 X ask 的请求与结果由 `platform_x` 拥有；Hacker News 的 ref、搜索选项与校验、条目字段（含讨论串的 `comments_delivered` 与 `order`），以及 stories 的请求、榜单与结果由 `platform_hn` 拥有；YouTube 的三种 kind（video、playlist、channel）的 ref 与 URL 解析、videos 的集合输入 `YoutubeCollection`（playlist 或 channel ref，或 `@handle`；它的文本形式可解析回自身，供 cursor 序列化）的解析、搜索选项与校验、fetch 选项（`--lang` ## Provider 契约与 registry

- **每 seam 一个 trait + 专属返回类型**：`WebSearch`/`DocsSearch`/`WebFetch`（supplemental 与主搜索共用 WebSearch 签名，registry 区分链序归属）；`SearchOutcome`/`DocsOutcome`/`FetchOutcome` 共享 ProviderAttempt/Source 构件。一个 provider＝一个 struct，同一 `Arc` 实例登记进多条 seam 链。
- **seam 支持矩阵**＝「谁 impl 了哪个 trait」的编译期事实；`order` 校验查 registry。**`map` 命令**＝tavily 直连操作（`site_map`），不设独立 seam trait（唯一 provider，需要时提升为 trait 是纯增量）；registry 在 tavily 描述内登记该操作。
- **凭据要求**：registry 的 `credentials`（`Credentials::Required`、`Optional` 或 `Unused`）是 provider 如何使用凭据的唯一来源。执行路径、doctor 与 smoke 用同一判定（`ProviderRegistration::is_configured`）决定「已配置」：需要凭据的 provider 要求 keys 非空，凭据可选与不需要凭据的 provider 恒为已配置。凭据可选的 provider（目前只有 Jina）有 `keys`，为空时以匿名方式运行；live smoke 只在它有 key 时运行其用例，doctor 深探与 live smoke 都只认带 key 的请求（结果含匿名 attempt 即报告 key 的失败），匿名路径由离线 fixture 覆盖。registry 校验与 smoke 的注册完整性检查都不要求 provider 需要凭据。
- **匿名执行**：不需要凭据的 provider 经 `execute_anonymous` 执行：不 claim、不轮换、不注入认证；每个 attempt 的 `anonymous` 为 true，`credential_index` 为 0，`rotation_count` 恒为 0，这两个字段对匿名 attempt 没有凭据含义。凭据可选的 provider 经 `execute_optional` 执行 Anonymous Fallback：凭据池为空时直接匿名执行；否则先按 `execute_v2` 的凭据池规则执行，以 Auth、QuotaExhausted 或 RateLimited 终止时，在同一 provider 槽位内用剩余时间再匿名执行一次，其 attempt 排在带 key 的 attempt 之后；其他错误类型不触发。匿名执行同样遵循共享重试策略，匿名 429 不重试。经凭据池发送的 attempt 与未发送请求的 Skipped/合成 attempt 的 `anonymous` 为 false。需要凭据的执行入口 `execute_v2` 遇到空凭据池时在发送前以 Auth 失败，不 panic。`execute_pinned` 只用池中指定序号的 key：不 claim、不轮换，因此不推进持久化的凭据游标，attempt 记录该序号，重试仍按共享策略；doctor 的逐 key 账户探针用它。共享构造器不断言 provider 需要凭据。
- **单次发送契约**：每次发送返回可选的 status 与解码值。现有调用方照常传入 status：多数 HTTP 调用方传入响应的实际 status，Exa 以及 Context7 的 MCP 调用成功时记为 200；非 HTTP 传输可以不带 status，attempt 的 `http_status` 随之为空。
- **传输类型**：registry 的 `transport` 声明 provider 到达上游的方式：`Http`，或 `OpenCli(OpenCliAdapter { site, contract })`。route adapter 从这一处读取 OpenCLI adapter 的 site 与契约版本；route 配置按传输类型与是否需要凭据使用 `HttpRouteRuntimeConfig`、`KeyedHttpRouteRuntimeConfig`（多一个 `keys`，供 factory 构造 Provider Credential Pool）、`ModelRouteRuntimeConfig`（再多一个 `model`，供请求模型的 route 使用）或 `ProcessRouteRuntimeConfig`；`PlatformRouteConfig::configured()` 把 keyed route 自己的 keys 交给注册信息的 `is_configured`，与 doctor 的 `provider_runtime` 同一判定；factory 的主机支持检查（process route 需要 Unix 进程组）、doctor 的检查方式与 checklist 测试的 R4 叶子都按传输类型分支，不按 provider id 分支；doctor 是否按 order 门控按 platform catalog 判定：不在任何平台默认 order 中的平台 route（process route 与 `youtube_web`）只在某个 order 启用它时参加 shallow 检查与 deep 探测。
- **registry 最小职责**（F10）：唯一登记 `ProviderId`、支持 seam、凭据要求、传输类型、访问策略、doctor probe、构造入口；注册合法性为「属于某个 Capability Catalog、某个 platform catalog，或拥有 operation 之一」，启动期校验、catalog 单测与 smoke 注册完整性检查共用 `catalog::has_owner`；config/doctor/capability status 从同一描述读取身份，不各设 allowlist；engine 只调用 seam trait 并聚合 `ProviderAttempt`，禁止按 provider id/model 分支。不引入宏、不生成 clap 树。

## Platform 维度

Platform 与 Capability Seam 并列（ADR 0019），完整接入契约见第 7 章。

- **platform catalog**：`catalog::PLATFORMS` 为每个平台登记平台 id、search 与 fetch 的 route 集合、只服务 L2 平台操作的 route（`operation_only`，例如 YouTube 的 `gemini_api`）、默认 order（`default_order`），以及已提升为 trait 的平台操作的 route 集合。平台的 route 成员（`all_routes`，也是 order 校验的依据）是 search、fetch 与 `operation_only` 三者的并集；不把 route 塞进它不实现的 search 或 fetch 集合。它是平台 route 隶属关系的唯一出处；Capability Catalog 集合保持原含义，不塞入平台 route。默认 order 只列该平台的 route，且不重复；需要用户手动启用的 route 是合法的 order 取值，但不出现在默认 order 中。platform catalog 的类型（`PlatformCatalog`、`PlatformOperation`）、各平台常量、`PLATFORMS`、`platform()` 查询与 HTTP 手动启用说明（`http_opt_in`：按平台当前 order 给出保留原有 route 的建议 order）在 `catalog` 的私有子模块 `capabilities/platform_catalog.rs` 中，经 `catalog` 再导出，调用方的 import 路径仍是 `catalog::…`；`catalog.rs` 保留 Capability Catalog、`ProviderId` 与 registry。
- **配置**：`platforms.<id>.order` 的默认值由 catalog 的 `default_order` 派生，不取 route 集合的并集。它以 `Rule::PlatformOrder` 对照 platform catalog 校验，拒绝重复项与不属于该平台的 route，允许为空（禁用平台）；文件加载与 `config set` 走同一规则，env 按既有公式派生。所有平台 route 的配置合成一个整体值 `PlatformRoutesRuntimeConfig`，`platform_route_config` 接收这个整体值，因此新增 route 时，runtime 投影、doctor 与 checklist 测试调用的函数签名都不变。runtime 投影为 `PlatformRuntimeConfig`，每项是 `SeamEntry<PlatformRouteConfig>`。
- **平台 seam trait**：`PlatformSearch` 与 `PlatformFetch` 不使用泛型，形状与兄弟 seam 相同，分别返回 `ProviderError` 或 `PlatformSearchOutcome`／`PlatformFetchOutcome`。factory 的 `build_platform_search` 与 `build_platform_fetch` 按 `PlatformRouteConfig` 的变体构造 route（route 身份由配置变体决定，不另传 `ProviderId`），`platform_search_support` 与 `platform_fetch_support` 调用 route 的纯函数支持检查；支持检查只读取请求（search 为选项与页位置，fetch 为深度），不联网。
- **平台链**：`platform_chain::plan_routes` 为每个平台操作做纯规划——可用 route＝order ∩ 该操作的 route 集合 ∩ 已配置 route；集合为空为 Config（退 3）；不支持显式选项的 route 记为 Skipped attempt（`error_kind` 为空），全部不支持为参数错误（退 2）；退 3 与退 2 的消息都为 order 未列出、只能由用户手动启用的 route 附启用说明（退 2 时只附支持该请求的 route；HTTP route 的说明由 `catalog::http_opt_in` 按当前 order 给出）；cursor 的 route 不能运行该请求（例如页位置不是它签发的）同样为参数错误。这些判定在进入链执行器之前完成。然后以共享链执行器按 `SlicedEven` 运行 route 链，沿用 LegitimateEmpty 语义，永不跨平台 fallback。search、Google Scholar cited-by 与 YouTube videos 是分页操作，共用同一规划、链执行与 cursor 编码；cited-by 与 videos 各只有一条 route，route 集合由 provider factory 的 `SCHOLAR_CITED_BY_ROUTES` 与 `YOUTUBE_VIDEOS_ROUTES` 声明，不进 platform catalog（第 7 章 L2 规则）。route 可以在执行中解析请求（videos 把 handle 解析成 channel）：分页链以解析后的请求生成结果页的 `collection` 与下一页 cursor。comments 是第二个单 route L2 操作，但不分页、不签发 cursor，也不复用 search 的请求与结果：`platform_comments` 按请求的平台分派 route 集合与支持检查（小红书为 factory 的 `XIAOHONGSHU_COMMENTS_ROUTES`，YouTube 为 `YOUTUBE_COMMENTS_ROUTES`），以同一 `plan_routes` 规划、同一链执行器运行，route 的成功一律采纳（空评论由 route 判定），结果为该平台形状的 `PlatformCommentsPage` 变体。X ask 是第三个，形状与 comments 相同：`platform_ask` 以 factory 的 `X_ASK_ROUTES` 规划，route 的成功一律采纳（回答不会为空）。Hacker News stories 是第四个：`platform_stories` 以 factory 的 `HN_STORIES_ROUTES` 规划，route 的成功一律采纳（空榜单是合法结果）。ask 按请求的平台分派 route 集合与支持检查（X 为 factory 的 `X_ASK_ROUTES`，YouTube 为 `YOUTUBE_ASK_ROUTES`），结果为该平台形状的 `PlatformAskResult` 变体。YouTube transcribe 是第五个：`platform_transcribe` 以 factory 的 `YOUTUBE_TRANSCRIBE_ROUTES` 规划。YouTube 的 ask 与 transcribe 是模型操作：规划时先经 `platform_precheck` 以 `plan_fetch` 规划一次条目读取（ask 读 `metadata`；transcribe 读 `abstract` 并允许描述为空，因为 Transcript 文件需要描述与章节），运行时先以 `platform_fetch::fetch_item` 读取条目，读取失败或直播中（Quality）即命令终态、不运行模型 route 链；读到的条目交给模型 route，前置检查的 attempts 与诊断由 `platform_precheck` 排在模型 route 链的 attempts 与诊断之前（成功与失败相同）。前置检查是 ask 规划结果中 YouTube 变体的一部分，X 变体没有前置检查，类型保证二者配对。模型 route 从不自己读取平台。
- **平台 fetch**：`platform_fetch` 以同一规划与链执行器运行 fetch route 链取得元数据；元数据失败即命令终态。`full_text` 深度下，答复的 route 在 `PlatformFetchOutcome.content_source` 中声明该版本的正文来源：一组按序读取的 URL（arXiv：HEAD 探测为 404 时只有 PDF，否则 HTML 在前、PDF 在后），或一个在同一 attempt 内校验过的本地文件（SSRN 浏览器下载的 PDF），或 route 在同一 attempt 内读到并核对过的 Markdown 正文（`FullTextSource::Native`，小红书；ADR 0022）。Native 来源不运行 Web Fetch，`platform_fetch` 直接用 canonical URL、route id 与正文构造 `PlatformContent`；`youtube_web` 的 Transcript 也是 Native 来源。`plan_fetch` 的计划按注册信息的 `native_full_text` 回答是否需要 Web Fetch，CLI 只在需要时预检 Web Fetch 配置。`platform_fetch` 对 URL 与本地文件两种来源用同样方式运行 `engine::fetch`，不含站点知识：URL 来源首个成功者即正文，有后续 URL 时本段最多使用剩余预算的一半，全部失败时以最后一条链的 `ProviderError` 为终态；本地文件来源只运行一次链。attempts 按元数据、探测、正文的顺序合并。正文落盘、原始文件的保留或删除与 `--format content` 的交付由 `cli/platform.rs` 负责，写入失败为 Runtime。
- **cursor**：`v1.<route>.<payload>`，payload 是 base64url（无填充）编码的 JSON 请求（search 为查询词、limit、选项与 route 自有的页位置；cited-by 另含被引 cluster，没有平台选项）。两种请求互不接受对方的字段，所以 payload 只能解码为其中一种操作。带 cursor 的请求只在该 route 上执行；route 已不可用、版本未知、无法解码、route 未知、属于其他平台或其他操作均为飞行前参数错误。
- **attempt target**：平台操作的 attempt 以 `AttemptTarget::Platform { platform, operation }` 序列化为 `{"platform", "operation"}`；链执行器的合成 attempt 使用调用方传入的 `AttemptTarget`。

## 错误模型

- **`ErrorKind` 10 变体**：Auth / RateLimited / QuotaExhausted / Parameter / Config / Timeout / Network / Quality / Evidence / Runtime。三方法：`is_retryable()`；`rotates_credential()`（RateLimited|QuotaExhausted——轮换优先于重试，429 不重试）；`family() → Transport|Content`（Quality/Evidence 为 Content 族）。**无 `exit_code()` 方法**。
- 「empty」从错误分类法除名：直连命令空结果＝`Ok(空 Outcome)` 退 0；证据管线的证据不足＝Evidence 退 5（域切分见第 1 章）。
- **退出码两阶段**：飞行前（argv→2、config/未知 env→3）只由预检产生；飞行后由**归因总函数**产生。attempt 级 Parameter 不映射退 2。
- **归因总函数**（F4 + #59 B3）：作用于单条 provider 链，只按每个 provider 的**最终 attempt** 归约（重试不参与计数），对各 kind 按**优先级全序**取最大，与重试次数、失败顺序无关。已有成功响应进入质量/证据阶段且终局失败＝Content 优先退 5，不被后续网络失败覆盖；所有可用 provider 均未产生可验证响应才退 4；同质失败顶层透传原 kind（如全 401 报 auth_error，退出码仍按族）；attempts 永远带原始 kind。
  - **全序表定稿**（低 → 高；Content 族恒高于 Transport 族）：`Network < Timeout < RateLimited < QuotaExhausted < Auth < Parameter < Runtime < Quality < Evidence`。定义域为**飞行后 kind**（ErrorKind ∖ {Config}）：`Config` 只在飞行前预检产生（退 3），**`ProviderAttempt` 不得携带 Config**——此为类型不变量，进 unit 真值表。族间关系与全序存在性为契约（真值表穷举验证）；族内排布编码期可微调，调整须同步更新真值表。
- `ProviderError`（thiserror）定义在 types 门面：kind + 脱敏消息 + attempts（每个 attempt 带 provider、status 与耗时）+ 非致命诊断；`forager::app::ProviderError` 作为再导出保留，types 下的新可达路径是预期结果。status→kind 映射只在 net 一份。
- **分类器已配置但失败**：降级继续 + stderr 警告 + journal 落痕，不影响退出码；research 裸调用下采用**固定最小降级 plan**（单步 web_search）继续执行（#59 H8）。
- miette 只渲染 text 人类报错；契约路径（JSON）不经 anyhow/miette。

## net 层

1. 全进程一个 `reqwest::Client`（rustls），构造参数单点。`net::build_client` 统一拥有 TLS、connect/read timeout、pool、User-Agent 与 `redirect::Policy::none()`；任何 provider endpoint 的 3xx 保留原 status，不请求 `Location`，经共享 status mapper 形成不可重试、不可轮换的 Runtime。当前不设 same-origin、provider 或状态码例外，也不构造第二个 client。
2. **`Deadline` 贯穿调用链**；main search 的主 backend 首次尝试可使用全部剩余预算，fallback backend 只消费失败后的残余。classifier 与辅助 seam 的 attempt 上限＝`min(层上限, 剩余预算 / 剩余必要 fallback 槽位数)`（F3）；耗尽→Timeout、保留已完成 attempts。辅助 seam 的槽位可执行定义见第 5 章 M17，main search 的边界与已接受后果见 ADR 0007。
3. SSE 只用 **eventsource-stream 裸解析**（不用 reqwest-eventsource——其自动重连绕过预算与 attempt 记录）；NDJSON 同入口换分帧器。
4. **`McpClient`** 统一 HTTP、Deadline、可选 session、JSON/SSE、JSON-RPC 与错误映射；只有 server 返回 session 时才发送 initialized notification 与后续 session header，缺 session 时直接 tools/call。session 过期重握手只服务实际发放 session 的 server，受同一 Deadline 约束。Context7 不发送旧 `X-Context7-Source`。`result.content` 存在但非标准数组时为 Runtime；structuredContent-only 路径继续可消费。**语义错误解码**（F5）：统一识别 JSON-RPC `error` 与 `result.isError`；可识别限流/配额文本映射 RateLimited/QuotaExhausted（触发轮换），未知 tool error 映射 Runtime 且不重试；归类先于轮换/重试决策。
5. `RetryPolicy` 参数化；可重试集合由 `is_retryable()` 决定；执行序固定：轮换 → 重试 → 上抛。
6. 4 MiB 成功截断仅属于 Web Fetch。xAI SSE、Exa JSON、Context7 MCP 保留 4 MiB 协议硬上限，超限整体为 Runtime，不从不完整协议包装合成成功；所有非 2xx 错误正文继续限制为 64 KiB。

## 主搜索流式终态与规范化

- xAI Search 与 ModelProbe 都发送 role-array input；xAI 必须看到 `response.completed`，completed 无 `output_text` 为 Runtime。failed/incomplete 按 payload code/status/reason 映射现有 ErrorKind，只有映射为 Network/Timeout 的终态重试，RateLimited/QuotaExhausted 轮换，其他保持非重试。
- 主搜索在完整响应组装后、attempt 判定成功前进入 normalizer：先删除完整闭合、大小写不敏感且可跨行的 `<think>...</think>`，再投影末尾显式 Sources/References/Citations/来源/参考资料/引用标题块与 `[[N]](HTTP(S) URL)`。不做策略/prompt-injection 关键词过滤，不解析 `sources(...)`、任意 `<details>` 或尾链猜测；规范化后 answer 为空为 Runtime。provider 引用注释中仅由数字构成的标题是引用序号而非页面标题，按无标题处理。来源按脱敏后的公开 URL 稳定去重。

## 凭据池

分界原则：跨进程必须共享的落盘，策略性短时效的留进程内。

- **池**：游标落盘 `$XDG_STATE_HOME/forager/credential_pool_state.json`，fs2 有界文件锁，「锁内取号推进 / 拿不到锁乐观降级」语义保持。**状态文件不变量**（F6）：带 schema version、只存非敏感索引；同目录 `0600` 临时文件 + fsync + 原子 rename；解析失败只复位受影响 provider 的游标并发非致命诊断，不升 config_error、不阻断搜索。`CredentialPool` struct 作为显式参数传入，无 reset 钩子。`classifier.keys` 走同一实现。
- **共享状态文件**：`state_file` 统一拥有状态目录解析（`XDG_STATE_HOME`，否则 `HOME/.local/state`，均须为绝对路径）、私有目录与有界文件锁、原子写，以及进程内串行化（咨询文件锁不能可靠排斥同进程内的其他句柄，因此同一状态文件的进程内读写经该文件的互斥逐个执行；调用方可以先限时等待轮次，再执行阻塞工作）。凭据池与跨进程限速共用它，各自决定锁不可用时的策略。

## 跨进程限速

`rate_limit` 统一负责跨进程请求节奏。访问策略包括最小间隔与最大并发，由 provider 注册信息的 `access_policy` 声明（`arxiv_api`：每 3 秒 1 个请求、并发 1；`ssrn_crossref`：每秒 1 个请求、并发 1；`ssrn_browser`：每 5 秒 1 次 OpenCLI 命令、并发 1；`xiaohongshu_browser`：每 10 秒 1 次 OpenCLI 命令、并发 1；`gemini_browser`：每 10 秒 1 次 OpenCLI 命令、并发 1；`chatgpt_browser`：每 10 秒 1 次 OpenCLI 命令、并发 1）；process 供应方以一次命令为限速单位，permit 持有到子进程被回收为止（ADR 0020）；对受限 endpoint 的每次发送（包括重试、doctor 的 shallow 可达性探测与 deep 探测）都必须先调用 `RateLimiter::acquire` 申请时间窗口。`providers::route_limiter` 按注册信息构造限速器；route adapter 在单次发送内先取窗口再发请求，窗口的等待计入该 attempt 与命令的 Deadline。

- **算法**：先在进程内按最大并发取得 permit，再取得跨进程连接槽位：状态目录下每个 route 有最大并发个槽位锁文件（`rate_limit_<route>.<n>.lock`），异步轮询到第一个空闲槽位；两段等待都计入 Deadline，超时为 Timeout。然后在 Deadline 内等到状态文件的进程内轮次（此时尚未预留，超时不会占用窗口），再在共享状态锁内读取该 route 上次预留的时刻，计算下一个窗口 = max(现在, 上次预留 + 最小间隔)。需要等待的时间不小于剩余预算时，直接以 Timeout 结束，不写入预留；否则写入新的预留时刻，释放锁，然后在锁外等待到该绝对时刻。permit 与槽位锁持有到发送结束，因此共享状态目录的所有进程同时在途的请求不超过最大并发；进程退出时操作系统释放槽位锁。
- **时钟**：预留时刻是墙钟毫秒，从构造时的墙钟起按 Tokio 时钟推进，因此预留、等待与 Deadline 在同一时间线上。
- **失败语义**：状态目录无法解析、锁在有界等待内拿不到、状态文件不可读或不可写时，不发送请求，以 Runtime 结束；不复用凭据池拿不到锁时「乐观降级」的策略。状态文件损坏或 schema 不符时，视为该 route 在当前时刻已有一次预留，因此修复后的第一个窗口仍间隔完整的最小间隔。
- **已知边界**：间隔按预留时刻保证，某个进程在预留之后被调度延迟时，实际发送间隔可能短于最小间隔，不做发送后复核；协调范围是共享同一状态目录的进程。

## web_fetch 薄正文质量门控

Web Fetch 成功值是 **Normalized Fetch Content**：从成功 provider 响应解码出的 provider 无关 Markdown 正文，不含传输包装、attempts 或 diagnostic。默认链为 `Firecrawl → Jina → Tavily`（ADR 0018、ADR 0029），直接 fetch、research 取证、search-side Web Fetch 与 PDF 都消费同一个 `engine::fetch`，不存在内容类型专属顺序。**Web Fetch 的输入是 URL 或带媒体类型的本地文件二选一**；每个 provider 有一个纯函数支持检查（Firecrawl 两者都接受，Tavily 与 Jina 只接受 URL），不能处理该来源的 provider 记一条 Skipped attempt，链中没有任何已配置 provider 能处理时以 Runtime 失败并写明来源类型。Tavily 固定请求完整 basic Markdown 且不传 query chunks；每个 Firecrawl provider attempt 只发送一次 `/scrape`（URL 来源）或一次 `/v2/parse`（本地文件来源，multipart 的 `file` 字段加 `options` 字段，响应形状与 scrape 相同，沿用同一个解码器），两者都显式请求 Markdown、`timeout: 60000` 与 PDF parser `{"type": "pdf", "mode": "auto", "pageMarkers": true}`（只对 PDF 生效，HTML 输出不变；ADR 0018），URL 来源另带 `onlyMainContent: true`；`providers.firecrawl.timeout` 默认 60 秒与之对齐；不发送 `waitFor`、actions 或第二套 rendering probe；Jina 通过官方结构化 JSON 响应的 `data.content` 读取正文，不启用链接删除或通用 selector。Firecrawl 以 HTTP 403 表示拒绝抓取目标站点（凭据失效为 401）；net 的共享 status mapper 把正文声明 `support this site` 的 403 记为 Parameter 而非 Auth，该 attempt 照常落到下一家，错误消息取 provider 响应的 `error` 文本。Jina 因滥用防护暂时拒绝匿名访问某个域名时返回 403，正文 `name` 为 `AbuseAlleviationError`；status mapper 同样记为 Parameter，错误消息取 Jina 的 `message`（含解封时间）。其余 403 与 401 仍为 Auth，402 仍为 QuotaExhausted。Jina 的匿名请求不发送 `Authorization`，其余请求头与带 key 时相同。

薄正文门只对 HTTP 成功并完成 provider 解码后的正文生效。两线命中任一 → `Quality`（Content 族）落下一家：**长度线**正文 < 200 字符；**密度线**唯一行数 ≤ 3 且总长 < 500。PDF（URL 以 `.pdf` 结尾，或媒体类型为 PDF 的本地文件）只适用长度线。全链皆薄 → 终态 Quality 退 5，attempts 带实测字符数。阈值为 types 具名常量，**不设配置键**。4 MiB 截断继续是成功加 diagnostic；只有截断后正文仍薄才 fallback。64 KiB 错误响应上限不变。

## Search Candidate 与 provider request contract

- `sources` 只保存 Primary Search Source；所有非主候选统一进入 `extra_sources`。Search Candidate 固定包含必填 provider/capability/provider_data 与可空 title/url/summary；URL 只能是真实 HTTP(S)，summary 只复制 provider-native 描述、摘要或片段，provider_data 是 snake_case 强类型白名单。
- Documentation Search 默认顺序为 Exa → Context7（ADR 0017）：Exa 返回可直接抓取的 URL 候选；Context7 只在 Exa 没有可消费候选时被自动调用，直连 `context7` 命令不受影响。research 在每个子问题的发现名额内按能力轮转分配候选，先声明的能力不能占满名额。
- Context7 Documentation Search 只做 library resolve，使用 `url: null` 与 typed library locator；Research 通过现有 Documentation Search seam 的 provider-owned query-docs 读取它。有 URL candidate 走 Web Fetch。Evidence Index 对 Context7 保留 `library_id`、`path`、`url: null`，Citation Binding 使用非链接 `[eN]`；URL evidence 使用 `[eN](URL)`。不建立通用 provider registry。
- Exa direct search 的 text/highlights 按请求 flag 精确投影并保留 image/favicon；Documentation Search 保留 highlights 与媒体选择信号但不读取全文。不强制 `useAutoprompt`，不以 `id` 代替必填 URL。
- Supplemental Tavily 请求显式发送 `search_depth: "advanced"`、`chunks_per_source: 1`（每条候选摘要至多一个约 500 字符的片段）、`include_raw_content: false`、`include_answer: false`；只有规范化后非空候选停止链。合法 `results: []` / `data.web: []` 继续 fallback，全链有合法空集且无非空结果时 `Ok(empty)`，`fallback=off` 只执行链头。仅跳过缺失/null/空白 URL 单项；非 HTTP(S) URL 单项同样跳过，其余合法候选保留；非字符串 URL、非对象条目、缺失或错误 container 为 Runtime。
- Tavily map 是 direct operation：CLI 校验 timeout `10..=150`、depth `1..=5`、breadth `1..=500`、limit > 0；合法 timeout 原样进入命令 Deadline 和 body，每个 attempt 再受 `providers.tavily.timeout` 与剩余预算较小值限制。
- 普通 search 在分类器决定能力集合后，让主搜索与辅助能力 fan-out 并发执行并共享同一绝对 Deadline（ADR 0016）；主搜索结束后按「分类器 attempts → 主搜索 attempts → 各能力分支（词汇表顺序）」合并。主搜索失败时，辅助 attempts 只追加用于诊断，已取得的候选与 capability gaps 由 `search_fanout::SearchFailure` 携带交付。
- search-side Web Fetch 成功结果以实际 provider 和 Normalized Fetch Content 的 300 字 preview 进入 `extra_sources`；抓取失败由 attempts、capability gap 和既有终态表达。Markdown 明确渲染 `Primary Sources` 与 `Extra Sources`；content 只返回主 answer；JSON、verbose 和 journal 消费同一结果角色。

## research 文件化交付

Research Evidence Pipeline 默认使用 standard 预算，将正文逐条写入 evidence Markdown，并只在成功 stdout 返回 Research Evidence Index。计划、未消费候选与 Research Recovery Manifest 分别写入 `00-plan.json`、`candidates.json` 与 `summary.json`；manifest 包含无正文的 evidence identity/metadata/path、coverage、gap、capability gaps、终态、attempts 与 `synthesis_policy`。未消费候选 artifact 以 `is_evidence: false` 明确其角色。失败 stdout 使用稳定小形状并以可空 `summary_path` 指向已成功写入且可直接读取的 manifest；locator 永不截断，极端长合法路径可超过 4 KiB 目标。

## journal

定位：结果面 + 过程面双记录。

- **结果面**：search 保存 query、answer 全文、仅属于主回答的 sources[] 与独立 supplemental candidates（含 search-side Web Fetch preview，URL 经统一脱敏器）；主搜索失败时保存 error_kind、message、已取得的完整 `extra_sources` 与 `capability_gaps`；research 保存 Evidence Index、coverage、artifact 路径与 capability gaps，不保存机械 answer/citations，也不重复 evidence 正文。
- **过程面**：plan 摘要（capabilities 终集 + 来源 + 分类器是否降级）、provider_attempts[]（provider、seam、error_kind、http_status、duration_ms、credential_index、retry/rotation 计数、`anonymous`（请求未发送凭据时为 true；匿名 attempt 的 credential_index 与 rotation 计数恒为 0）、脱敏截断 500 字符错误消息、model、endpoint_host）、终态归因、budget 视图 `{total_ms, consumed_ms, exhausted}`、分类器耗时、capability_gaps。
- **字段白名单排除项**：请求/响应头、请求体、原始响应体、key 任何形式（含掩码）、分类器 prompt 原文。
- `capability_gaps` 形状：`[{capability, reason: no_configured_provider|partial_failure|all_attempts_failed, providers_skipped[]}]`，空则省略；结果 JSON 顶层 + stderr 警告 + journal 三出口。
- **落笔机制**（F7 修订）：`app` 层唯一终态写入器落笔一次，Ok/Err 皆写；panic hook 只做最小 stderr 诊断、**不写 journal**；孤儿任务 panic 与 kill -9 丢记录为已接受限制。
- **路径规则**（F8）：`journal.dir` 只支持前导 `~/` 展开；相对路径统一相对 config 目录解析（不依赖 cwd）；`FORAGER_CONFIG_DIR` 改变 config 目录时同步改变该基准。
- 深钻只投影现有 attempts：debug 在命令终结时至多一条脱敏摘要，trace 再输出逐 attempt 安全字段；error/warn/info 不新增可选日志。日志不持久化，也不输出 attempt message、model、endpoint、请求/响应、正文、header、credential、prompt 或 tool trace。
- journal 每次调用写独占 `search_result_<nanos>_<pid>_<seq>.json` 并 `sync_all`；retention 只删除完整匹配该命名且过期的普通文件。其他 JSON/JSONL、相近名称、目录和链接不属于 forager 所有权。

### YouTube 职责

`youtube_api` 是 YouTube 平台的官方 route，经 YouTube Data API v3 与用户自己的单个 key 交付 search 与 fetch 的 `metadata`、`abstract`（ADR 0028）。`providers/youtube_api.rs` 是入口：`YoutubeApi` 结构、keyed GET 传输（经 `execute_v2`，每次发送先取访问限速窗口，key 只放在 `X-Goog-Api-Key` 请求头）、错误体 reason 识别（`API_KEY_INVALID` 为 Auth，`quotaExceeded`/`dailyLimitExceeded` 为 QuotaExhausted，经 net 的 reason 钩子生效）与失败消息（上游消息经共享 markup 模块转成纯文本）、`videos` 资源 DTO 与解码（ISO 8601 时长、直播状态推导、计数与字幕标志），以及 fetch 的支持检查与 inherent 方法 `YoutubeApi::fetch`（不存在的视频为 attempt 级 Parameter，`abstract` 缺描述为 Quality）。私有子模块 `providers/youtube_api_comments.rs` 拥有 L2 操作 `YoutubeApi::comments`：一次 `commentThreads.list` 的请求、thread 与回复解码（videoId 核对、`replies_complete`）与关于视频的失败的消息改写：评论关闭（`commentsDisabled` 由入口模块的 reason 识别归为 Parameter）与视频不存在（404 `videoNotFound`，改用与 fetch 相同的消息），入口的 `get_with` 让操作改写失败消息。私有子模块 `providers/youtube_api_videos.rs` 拥有 L2 操作 `YoutubeApi::videos` 与它的支持检查：channel 或 handle 的第一页经 `channels.list` 解析出 uploads 播放列表（不存在为 Parameter），channel 的页位置携带它（`<playlist>:<pageToken>`），后续页不再解析；`playlistItems.list` 的请求与条目解码（视频所有者为频道、`videoPublishedAt` 为发布时间、`position`、描述片段截断）、跳过私有与已删除条目并汇总诊断、playlist 404 的消息改写，以及多个请求的 attempt 累积。私有子模块 `providers/youtube_api_search.rs` 拥有 search 的支持检查、选项到 `search.list` 参数的映射、检索结果解码（HTML 实体还原），以及用一次 `videos.list` 批量补全时长、计数与字幕标志的增强：增强失败时保留检索结果并汇总一条诊断。平台路由配置 `PlatformRouteConfig::YoutubeApi` 携带 `KeyedHttpRouteRuntimeConfig`；配置 schema 以 `Rule::AtMostOne` 拒绝多于一个的 key。`youtube_api` 的 fetch 支持检查拒绝 `full_text` 时只说明 Data API 不提供字幕；启用 `youtube_web` 的命令与风险说明由 `platform_chain` 经 `catalog::http_opt_in` 附在参数错误与配置错误之后。

`youtube_web` 是 YouTube 平台只服务 fetch 的匿名 route，读取 YouTube 网页与未公开的播放器和字幕接口，交付 `metadata`、`abstract` 与 `full_text`（ADR 0028）；它不在默认 order 中。`providers/youtube_web.rs` 是入口：`YoutubeWeb` 结构、一次 fetch 固定顺序的三个请求（watch 页、ANDROID 客户端的 `/youtubei/v1/player`、选中字幕轨的 srv1 XML；经 `execute_anonymous`，每次发送先取访问限速窗口，不重试，后一个请求失败时带上之前的全部 attempt）、客户端名称、版本与请求体形状的唯一常量块（以 youtube-transcript-api 为参照）、watch 页解码（InnerTube key、页面内嵌的播放器响应、没有 key 时按机器人验证页区分 Auth 与 Runtime）、播放器响应解码（playability 到错误类型的映射、videoId 核对、由 videoDetails 与 microformat 构造条目、直播状态推导），以及 fetch 的支持检查与 inherent 方法 `YoutubeWeb::fetch`；每个判定都在读取对应响应的 attempt 内做出。私有子模块 `providers/youtube_web_captions.rs` 拥有字幕轨：原始语言的推断（唯一一条 ASR 轨的语言，条目只报告它；否则播放器默认字幕轨的语言，只用于选轨）、选轨规则（无 `--lang` 时原始语言的发布者字幕、再其 ASR 字幕；有 `--lang` 时按优先级先找发布者字幕、再找 ASR 字幕；从不使用机器翻译）与无轨消息、srv1 地址（去掉 `fmt`、同源检查、拒绝需要 PO Token 的地址），以及 srv1 XML 到 Transcript 分段的解码（XML 反转义后经 `providers/markup` 转纯文本，跳过空白分段）。`youtube_web` 经 `providers/youtube_transcript` 渲染 Transcript，作为 Native 正文交给 `platform_fetch`。平台路由配置 `PlatformRouteConfig::YoutubeWeb` 携带 `HttpRouteRuntimeConfig`；它只服务 fetch，`build_platform_search` 对它的分支不可达。

`providers/transcript.rs` 是与平台无关的共享模块，拥有 Transcript：分段（`{start_ms, end_ms, text}`，由秒构造时校验时间有限、非负、结束不早于开始与文字非空，允许重叠与静音间隔）、章节输入（自有类型，不依赖平台叶子）、头部条目字段，以及渲染：头部按来源区分的说明、「Description」与「Transcript」两节、章节边界断段并以章节标题为小节标题、章节内约 45 秒或 2 秒以上静音断段（有标点的来源优先在句末断段，到 90 秒强制断段）、分段文字内部空白的折叠与段内分段的连接（汉字、假名与全角标点之间不加空格）、每段开头由调用方提供的「秒 → 回看 URL」函数生成的时间戳链接。它返回 Markdown 与 `TranscriptInfo`。生产方是 `youtube_web`（`manual`/`asr`）与 `gemini_api` 的 Transcribe（`model`）；`model` 来源的头部注明 Transcript 由模型生成、不保证逐字。

`providers/youtube_transcript.rs` 是两个生产方共用的 YouTube 绑定，依赖 `providers/transcript` 与 `types`，不依赖任何 route adapter：`YoutubeVideo` 把一个 YouTube 视频条目（ref 与平台字段；非 YouTube 条目不可达）交给渲染，由条目构造头部字段（标题、ref、频道、发布时间、时长），把 `YoutubeChapter` 转成 Transcript 章节，回看链接取 `YoutubeRef::moment_url`（`<canonical URL>&t=<秒>s`）。描述与章节由生产方给出：`youtube_web` 由描述解析章节，`gemini_api` 取前置检查读到的条目。

`cli/youtube.rs` 是 `cli/platform.rs` 的私有子模块，负责 YouTube 的参数树、`--channel` 的 channel ref 或 URL 解析、`--lang` 到 `PlatformFetchOptions::Youtube` 的转换与类型化请求构造（构造后运行 `PlatformFetchRequest::validate`），在飞行前拒绝把 playlist 或 channel 交给 fetch 与 comments，并把 videos 的集合输入或 cursor 交给 `cli/platform.rs` 的分页入口（`platform_chain::plan_videos` 与 `plan_cursor_videos`）；comments 经 `cli/platform.rs` 共用的 comments 入口执行，ask 经它共用的 ask 入口执行（X 与 YouTube 共用）；ask 与 transcribe 的 `--timeout` 默认 600 秒（模型读完长视频需要数分钟），transcribe 的 Transcript 文件名为 `youtube-<id>-transcribed.md`，经 `cli/platform.rs` 与 fetch 共用的落盘入口写入。

`gemini_api` 是只服务 YouTube 的 ask 与 transcribe 的模型 route，经 Gemini 原生 `generateContent` 协议与用户自己的 key 池请求模型，端点可配置（ADR 0028）；它不在任何平台的 search 或 fetch 集合中，只登记在 YouTube 的 `operation_only`。`providers/gemini_api.rs` 是入口：`GeminiApi` 结构、请求体（一个 `fileData {mimeType: "video/*", fileUri: <canonical URL>}` 部分与一个指令文字部分，不使用 `videoMetadata`）、keyed POST 传输（经 `execute_v2`，每次发送先取访问限速窗口，key 只放在 `x-goog-api-key` 请求头；凭据池按共享规则在 429 时换 key）、错误体的失败消息（`Gemini API returned HTTP <status> (<STATUS>): <message>`）、响应解码（跳过 `thought` 部分；prompt 被拦截、`finishReason` 为截断或安全类为 Quality，其他非正常结束与没有候选为 Runtime；`modelVersion` 与 `usageMetadata` 映射为 `model` 与 `usage`），以及 inherent 方法 `GeminiApi::ask`（回答为空为 Runtime）、`GeminiApi::transcribe` 与 doctor 深探 `GeminiApi::accounts`（逐 key `GET <url>/models`，经 `execute_pinned`，不经凭据轮换）。私有子模块 `providers/gemini_api_transcript.rs` 拥有 transcribe 的指令、`generationConfig`（`responseMimeType=application/json` 与 `{language, segments: [{start, end, text}]}` 的 `responseSchema`），以及模型输出到 Transcript 的校验与渲染：JSON 无效、语言为空、分段时间非法或没有分段为 Quality；结束时间超出条目时长 5 秒以上的分段丢弃并汇总一条诊断；章节与描述取前置检查读到的条目；经 `providers/youtube_transcript` 以 `model` 来源渲染。平台路由配置 `PlatformRouteConfig::GeminiApi` 携带 `ModelRouteRuntimeConfig`；`build_platform_search` 与 `build_platform_fetch` 对它的分支不可达；factory 的 `route_accounts` 把它与 `serpapi` 一同映射到 `KeyAccount`（额度为 `KeyQuota::Unreported`，doctor 的 `keys` 项不带额度字段）。

### Gemini Deep Research 职责

`gemini_browser` 是不属于任何 catalog 的 process 供应方，以拥有操作 `gemini_research_start`、`gemini_research_result` 满足 `catalog::has_owner`（ADR 0023）。`cli/gemini.rs` 拥有 `forager gemini` 的参数树、会话参数解析（飞行前退 2）、供应方构造，并以文件名前缀 `gemini` 调用 `cli/delegated_report.rs` 的共享落盘规则（`gemini-<id>.md` 与 `gemini-<id>.sources.json`；默认写入按调用隔离的临时目录，`--report-dir` 覆盖，写入失败为 Runtime，不回退为内联输出），`result` 与 `start` 的结果分别由 `CommandOutput::GeminiResearch` 与 `CommandOutput::GeminiResearchStart` 交给二进制侧的 `cli/gemini_render.rs` 渲染。`infra/types/gemini_research.rs` 拥有会话 id（URL 或十六进制 id 的解析与 canonical URL）、计划与进度的公开形状（报告与来源用 `delegated_report` 的共享形状）、`result` 与 `start` 的成功载荷序列化，以及带已知会话的失败形状（二进制侧渲染为 `conversation_url`）；`result` 的结果另带报告文件路径，报告本身只含 Gemini 交付的内容；两个操作名只在 crate 内可见。`providers/gemini_browser.rs` 是供应方入口，拥有 OpenCLI 命令构造（`start` 声明前台窗口，`report` 与 `status` 声明后台窗口）、执行设置（`result` 沿用共享重试策略，`start` 与 `status` 只执行一次）、`start` 失败时补上已知的会话 URL、页面事实分类（未登录优先，其次页面提示、停在 `/app` 首页、显示的是另一个会话、缺响应体与超时）与会话 id 核对；私有子模块 `providers/gemini_browser_start.rs` 拥有 `start` 页面事实的分类：登录、错误码与额度提示、发送前停下、计划或普通文本、确认是否点到、研究是否开始与最终页面，以及进程本身失败时“结果未知”的提示；私有子模块 `providers/gemini_browser_decode.rs` 是纯函数解码：batchexecute 与 `StreamGenerate` 帧、JSPB 字段（含末尾扩展对象）、最新研究轮次的选取与严格判定（不回退到较早的报告），以及计划、进度、报告与来源的解码，`StreamGenerate` 的会话 id、错误码、计划回复与研究开始的判定，结构不符时给出位置。factory 的 `adapter_status` 构造它并运行 `status`，是 doctor 深探 `DoctorProbe::AdapterStatus` 的实现；doctor 按传输类型与是否属于平台 catalog 决定跳过浅检，不按 provider id 分支。

`skills/forager/opencli/forager-gemini/` 是它的读取模块：`shared.js` 拥有截止时间、轮询等待、页面事实（最终 URL、是否要求登录、会话不可用提示）、按 Resource Timing 计数已完成的被跟踪调用（batchexecute 的某个 rpc id，或 `StreamGenerate`）、读取抓包前保证响应体已存好的多一次页面往返、按同一标识读取抓包，以及所有顶层导航共用的导航步骤：先在 `gemini.google.com` 开启抓包并清空已抓条目，再打开页面（OpenCLI 扩展在未开启抓包的标签页上导航前会断开调试器，Chrome 拒绝这次导航；清空保证之后读到的只有本次导航起的请求）；`report.js` 先开始抓包再打开 `/app/<id>`，等到第一个 `hNvQHb` 调用完成并多做一次页面往返后才读取抓包，返回其响应体，截止时仍返回合法外壳并标记 `timed_out`；`start.js` 先开始抓包再打开 `/app`，依次展开工具菜单、选择 Deep Research、填写问题、点击发送、等第一轮 `StreamGenerate` 完成与计划卡片、点击确认、等第二轮完成，发送与确认各至多一次，记录到达的步骤，停下或截止时仍返回合法外壳与两轮响应体；`status.js` 打开 `/app` 并报告登录状态；`contract.js` 报告契约。

### ChatGPT Deep Research 职责

`chatgpt_browser` 与 `gemini_browser` 同形：不属于任何 catalog 的 process 供应方，以拥有操作 `chatgpt_research_start`、`chatgpt_research_result` 满足 `catalog::has_owner`（ADR 0023），访问受 ADR 0024 的条件约束。`cli/chatgpt.rs` 拥有 `forager chatgpt` 的参数树、会话参数与空问题的飞行前校验（退 2）、供应方构造，并以文件名前缀 `chatgpt` 调用 `cli/delegated_report.rs` 的共享落盘规则；`result` 与 `start` 的结果分别由 `CommandOutput::ChatgptResearch` 与 `CommandOutput::ChatgptResearchStart` 交给二进制侧的 `cli/chatgpt_render.rs` 渲染。`infra/types/chatgpt_research.rs` 拥有会话 id（`/c/<uuid>`、`/g/<project>/c/<uuid>` 或裸 UUID 的解析、小写归一与 canonical URL）、计划与进度的公开形状（与 Gemini 的形状不同，不合并；报告与来源用 `delegated_report` 的共享形状）、`result` 与 `start` 的成功载荷序列化，以及带已知会话的失败形状；两个操作名只在 crate 内可见。`providers/chatgpt_browser.rs` 是供应方入口，拥有 OpenCLI 命令构造（`start` 声明前台窗口，`report` 与 `status` 声明后台窗口）、执行设置（`result` 沿用共享重试策略，`start` 与 `status` 只执行一次）、`start` 失败时补上已知的会话 URL、页面事实分类（未登录优先，其次页面提示、被送回首页、显示的是另一个会话、缺响应体与超时）、会话身份核对（页面 URL 与响应的 `conversation_id`）以及用量回执超限时 QuotaExhausted 失败的措辞；私有子模块 `providers/chatgpt_browser_start.rs` 拥有 `start` 页面事实的分类：登录、发送后的额度提示、发送前停下（附草稿是否已清空）、是否得到会话、重新打开会话后读到的研究状态（研究中或已完成为成功，倒计时后仍在等待开始、普通文本回复与用量回执超限为失败）、计划出现后没有读到会话，以及进程本身失败时“结果未知”的提示；私有子模块 `providers/chatgpt_browser_decode.rs` 是纯函数解码：会话响应的扁平消息列表、最近研究消息的选取（不回退到较早的研究）、`widget_state` 的二次解析与严格判定（研究开始前没有 `widget_state` 时，只在快照 `venus_widget_state` 仍等待计划确认时按快照判定）、用量回执与当前状态的权衡（研究中或已完成时以状态为准，否则超限回执决定；`result` 与 `start` 共用）、计划（任意状态下都可取）与进度、最近一条有文字的 assistant 回复，结构不符时给出位置；私有子模块 `providers/chatgpt_browser_citations.rs` 拥有引用改写：按 `grouped_webpages` 条目的字符区间替换私有区标记、去掉 `utm_source=chatgpt.com` 并去重、全报告按首次出现编号、标题回退与残留标记检查；私有叶子模块 `providers/chatgpt_browser_shape.rs` 拥有解码与引用改写共用的 JSON 游标（值及其自响应根起的路径）与带位置的结构错误，依赖单向：解码依赖引用改写，两者都依赖该叶子，叶子不依赖任何一方。factory 的 `adapter_status` 同样为它运行 `status`。

`skills/forager/opencli/forager-chatgpt/` 是它的读取模块：`shared.js` 拥有截止时间、轮询等待、页面事实（最终 URL、是否要求登录、会话不可用提示）、按 Resource Timing 计数已完成的 `GET /backend-api/conversations/<uuid>`、读取抓包前保证响应体已存好的多一次页面往返、按同一路径读取抓包，以及所有顶层导航共用的导航步骤：先在 `chatgpt.com` 开启抓包并清空已抓条目，再打开页面（OpenCLI 扩展在未开启抓包的标签页上导航前会断开调试器，Chrome 拒绝这次导航；清空保证之后读到的只有本次导航起的请求）；`report.js` 先开始抓包再打开 `/c/<uuid>`，等到该请求完成并多做一次页面往返后才读取抓包，返回其响应体，截止时仍返回合法外壳并标记 `timed_out`；`start.js` 打开首页，必要时把撰写器切到“聊天”，先输入问题再从“添加文件等内容”菜单选择“深度研究”，核对输入框同时含问题与指向 `app://connector_openai_deep_research` 的提及标记，点击发送，等页面进入 `/c/<uuid>`，再等计划卡片的沙箱 iframe（按域名或标题识别，内容不可访问）或普通回复，出现卡片时保持标签页打开到计划倒计时之后（有上限，并给重新打开留出时间），然后先开始抓包再重新打开会话并读取会话响应；发送至多点击一次，不点击计划卡片，所有点击与输入都经 OpenCLI 的浏览器原语，发送前停下时清空输入框并回报是否清空，记录到达的步骤，停下或截止时仍返回合法外壳；`status.js` 打开首页并报告登录状态，不切换撰写器模式，不打开菜单；`contract.js` 报告契约。读取模块不读取 cookie 或令牌，不自行发请求，也不改写页面的 fetch、XHR 或 WebSocket。
